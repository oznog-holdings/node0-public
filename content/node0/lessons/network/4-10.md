This is a design correction rather than an incident, and it is here because
it changed a real decision on 20260817, before that decision became
expensive to reverse: a long high-speed cable run between racks that the
existing plant could not support anyway.

The earlier reasoning had genuine appeal. Spread a switch pair across two
racks, using multi-chassis link aggregation so a host's two uplinks land on
two switches that behave as one. Then a host keeps a working link even if
its own rack's network hardware fails entirely. Written down that way it
sounds like more redundancy for the same money.

It assumed that the thing doing the actual routing, the shared gateway
addresses every host depends on to reach anything outside its own segment,
lived somewhere safe from that failure. It did not. The routing pair sat in
the same rack as most of what it served, so a host's own rack dying was
already fatal to it, with or without a surviving cable to a switch
elsewhere. The design bought a link that would survive in a scenario where
the host it served would not.

The habit worth keeping is to state explicitly which failure domain a
redundancy design is protecting against, then check whether the shared
infrastructure the design depends on sits inside that same domain. When the
answer is that it does, the honest move is the one taken here: build the
simpler thing, write the single point of failure down in the runbook, and
accept it on purpose rather than discovering later that you had been
assuming otherwise.
